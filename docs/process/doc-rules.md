# 文档规范

| 项 | 值 |
| --- | --- |
| 状态 | 生效，v1 |
| 最后更新 | 2026-11-27 |
| 适用范围 | 本仓 `docs/` 与根目录文档 |

## 1. 目录与职责

```text
docs/
├── README.md                    # 导航：先读这个
├── requirements/                # 要什么、为什么、验收口径
├── tech/                        # 怎么做：协议、决策、SDK、移动端、密钥
├── test/                        # 怎么验：计划、追溯矩阵、真机清单
└── process/                     # 怎么推进：迭代、文档规则（本文件）
```

一条硬规则：**同一份事实只写在一个地方**。其他地方写一句链接。复制粘贴的结果一定是两边不一致。

## 2. 命名

| 类型 | 文件名 | 说明 |
| --- | --- | --- |
| 需求 | `requirements.md` | 一类一份 |
| 协议 | `protocol.md` | 一类一份 |
| 测试计划 | `test-plan.md` | 一类一份 |
| 验收 | `acceptance.md` | 一类一份 |
| 专题设计 | `sdk.md`、`mobile.md`、`decisions.md`、`key-registry.md` | 一个主题一份 |
| 流程 | `iteration.md`、`doc-rules.md` | 一类一份 |

**文件名一律不带版本号，也不带日期。** 版本是文档头表格里的字段，不是文件名的一部分——`protocol-v1.md`、`protocol-v2.md` 并排躺着，正是要避免的文档垃圾。

**一个主题只有一份现行文档，原地更新。** 历史交给 git（`git log -p docs/tech/protocol.md`）和 `CHANGELOG.md`，不靠复制副本。要查“当初长什么样”，回到对应的 tag 看。

## 3. 文档头

每篇 `docs/` 下的文档开头必须有这张表（专题设计可省“关联协议”以外的一两行）：

```markdown
| 项 | 值 |
| --- | --- |
| 状态 | 草案 / 生效 / 已冻结 / 已废弃 |
| 文档版本 | v1（原地递增，不改文件名） |
| 最后更新 | YYYY-MM-DD |
| 关联需求 | [`requirements.md`](../requirements/requirements.md) |
```

**状态的含义**要当真：

- 草案：可以推翻，别照着实现；
- 生效：可以照着做，改动走 PR；
- 已冻结：只有升版本才能改；
- 已废弃：内容已合并进别处或不再适用，不要引用；下一次清理时直接删掉文件。

## 4. 模板

### 4.1 需求

```markdown
## 1. 背景与场景
## 2. 角色
## 3. 范围（做 / 不做）
## 4. 功能需求（FR-xx，含优先级与验收口径）
## 5. 非功能需求（NFR-xx，含目标值）
## 6. 约束与假设
## 7. 变更记录
```

要求：每条 FR 都要有**可判定的验收口径**（能回答“怎么算做到了”），编号一旦分配就不复用于新需求。

### 4.2 技术

```markdown
## 1. 目标与约束
## 2. 方案（含被否掉的方案与原因）
## 3. 关键实现要点
## 4. 与协议/需求的关系
## 5. 风险与待定项
```

要求：写取舍，不抄代码。能被代码本身表达的（函数签名、常量）就别抄进来，抄了一定会过期。

### 4.3 测试

```markdown
## 1. 目标
## 2. 分层与覆盖
## 3. 环境与数据
## 4. 用例 / 追溯矩阵
## 5. 通过标准与退出条件
## 6. 风险
```

要求：每条用例能追溯到一条需求编号；没有编号的“顺手测一下”不算用例。

## 5. 同步检查点

提交前问自己三句：

1. 改了行为没？→ 测试文档的追溯矩阵状态要不要动？
2. 改了字节语义没？→ 协议 + 决策记录 + 向量 + 两个实现仓的 `compatible:` 四件都动了吗？
3. 新增了取舍没？→ `tech/decisions.md` 加一条，别让决定只活在提交信息里。

完整矩阵见 [`iteration.md`](iteration.md) §7。

## 6. 禁止事项

- 需求文档里写实现细节（“用 AES-CTR”不属于需求）；
- 技术文档里写需求（“用户需要……”留给需求文档）；
- 把密钥、真实文档、`.jm` 样本提交进仓库（`testvectors/` 的公开测试密钥除外）；
- 用 `docs/` 存临时笔记——临时东西放本地或 issue；
- 让文档里的命令跑不通。文档里的每条命令都应当能直接复制执行。

## 7. 维护与清理

文档会腐坏，也会堆积。要求是**仓库里永远只有当前有效的内容**：

- 内容过期就**改写或删除**，不留“已废弃”章节层层叠加；
- 拆分/合并不留原文副本，也没有 `archive/`、`old/`、`v2` 这类目录；
- 迭代过程记录（验收结果、临时清单）写在 PR 描述里，PR 合上就进 git 历史，**不进仓库文件**；
- 每轮迭代收口时做一次清理：删过期段落、并重复内容、扫死链（相对路径最容易断）；
- 新增一个文档之前先回答：“为什么不能并进现有某个文件？”答不上来就别新增；
- 这条规则有机器兜底：`docs/` 下的文件白名单写在 [`.github/scripts/check_docs.py`](../../.github/scripts/check_docs.py)，加文件就得改白名单，CI 会拦。

判断某条内容该不该留下的标准只有一个：**半年后还会有人照着它做事吗**。不会，就删。
