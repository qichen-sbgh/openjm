## 1. 背景与场景

群里发一份 PDF，发的人不想让平台知道这是什么、也不想被群文件的风控拦下；收的人只想点开就看，不想装一堆东西、不想每次输密码。

```text
发送方：本地 PDF ──[SDK 封装]──▶ doc_20261127_a1b2c3d4.jm ──[QQ 群文件]──▶
接收方：QQ 里点一下 ──[唤起 App]──▶ 校验、解密 ──▶ 进书架 ──▶ 原生渲染阅读
```

两端的形态刻意不对称：**发送端没有 GUI，只有 SDK**；**接收端只有 App，没有导出功能**。

## 2. 角色

| 角色 | 关心什么 | 对应能力 |
| --- | --- | --- |
| 发送方 | 一条命令封完、能塞进自动化脚本、群文件不被拦 | SDK + CLI |
| 接收方 | 点开即读、不重复输密码、有书架和进度 | App |
| 维护者（当前只有你） | 三端不跑偏、改动可追溯、发布可回滚 | 协议规范 + 向量 + 迭代规约 |

## 3. 范围

**做**：PDF 的封装、分发、唤起、校验、解密、书架、阅读、进度记忆。

**交付顺序**：Android 先跑通并稳定，iOS 在 Android 稳定后对齐（决策见 [`decisions.md`](../tech/decisions.md) D10）。这个顺序只影响排期，不改变下面各条需求的优先级判断。

**不做**（写进非目标，防止后面被“顺手加上”）：

- 不做阅后即焚、不做有效期、不做水印；
- 不做明文导出与分享（文档进沙盒后只在该 App 内可见）；
- 不做高强度密码学对抗（见 §6 约束）；
- 不做服务端：没有账号、没有上传、没有云端书架；
- 不做 PDF 以外的格式（协议已预留 `ext`，但 v1 不实现）。

## 4. 功能需求

优先级：P0 不可缺、P1 首版应有、P2 可延后。验收编号对应 [`acceptance.md`](../test/acceptance.md)。

### 4.1 发送端

| 编号 | 需求 | 优先级 | 验收口径 |
| --- | --- | --- | --- |
| FR-01 | 提供无 GUI 的 Python SDK，能被批处理脚本与 QQ 机器人流水线直接调用 | P0 | 一条命令完成封装；单文件依赖 ≤ 1 个第三方库 |
| FR-02 | 输出文件名脱敏为 `doc_YYYYMMDD_xxxxxxxx.jm`，真实文件名只存在于加密 Meta | P0 | 文件名不含原文任何片段；解密后能还原原名 |
| FR-03 | 同一份 PDF 反复封装，输出不得有字节级关联（抗哈希指纹、抗固定体积指纹） | P0 | 两次封装字节不同、长度不同、`doc_id` 相同 |
| FR-04 | 支持可选口令模式，日常分发默认零输入 | P1 | 不带口令可直接打开；带口令时首次导入需输入一次 |
| FR-05 | 支持只校验不解密（给流水线做预检） | P1 | CLI 能只看头部、只验完整性 |
| FR-06 | 封装过程原子落盘，中断不留半个可用文件 | P0 | 中断后目标路径无残留、无半成品 |

### 4.2 分发与唤起

| 编号 | 需求 | 优先级 | 验收口径 |
| --- | --- | --- | --- |
| FR-07 | Android 能从 QQ 直接唤起（含 `application/octet-stream`、无后缀 `content://`、被改名成 `.jm.1` 的情况） | P0 | 四家国产 ROM 真机点击可进 App |
| FR-08 | Android 提供 SAF 手动导入入口，作为 ROM 拦截文件关联时的兜底 | P0 | 首页有“导入 .jm”，选择器可选本地文件 |
| FR-09 | iOS 能出现在 QQ“用其他应用打开”列表，并通过 `onOpenURL` 接住 | P0 | 真机列表可见 openjm，点击可进 App |
| FR-10 | 非 `.jm` 文件被误点开时要友好退出，不崩 | P1 | 传任意文件给出明确提示 |

### 4.3 接收端

| 编号 | 需求 | 优先级 | 验收口径 |
| --- | --- | --- | --- |
| FR-11 | 下载不完整、被截断、被篡改必须识别并提示重新下载，绝不把残缺数据送进渲染器 | P0 | 截断 1 字节即报错；与口令错误区分不了时按同一提示处理 |
| FR-12 | 校验通过后解密进私有沙盒，不留 `.jm` 副本，节省一半空间 | P0 | 导入后沙盒内只有明文 PDF，无 `.jm` |
| FR-13 | 书架按 `doc_id` 去重；同一文件被重复发来时不丢阅读进度 | P0 | 重复导入后进度、总页数保持 |
| FR-14 | 书架展示封面与进度，默认按最近阅读排序 | P1 | 有封面、有进度标签 |
| FR-15 | 阅读进度（页码 + 滚动比例）自动保存，切横竖屏不跑偏 | P0 | 杀进程重进恢复到上次位置 |
| FR-16 | 用平台原生渲染 PDF，避免 ROM 字体缺失与缩放模糊 | P0 | 复杂排版 PDF 显示正常，缩放清晰 |
| FR-17 | 口令文件首次导入验证一次，之后免密续读 | P1 | 二次打开不再弹口令 |

### 4.4 演进预留

| 编号 | 需求 | 优先级 | 验收口径 |
| --- | --- | --- | --- |
| FR-18 | 协议预留扩展名与算法位，后续可支持 EPUB / 图片集 / 音视频 | P2 | 加新格式不需要升协议版本 |
| FR-19 | 超大 PDF 支持零落盘按需解密（按页 Seek） | P2 | 已发出的 v1 文件无需改动即可受益 |

## 5. 非功能需求

| 编号 | 需求 | 目标值 |
| --- | --- | --- |
| NFR-01 | 加解密性能 | 50MB PDF 解密 30–80ms 量级（硬件 AES） |
| NFR-02 | 内存占用 | 全链路流式，峰值与文件大小无关（≈ 64KB 缓冲） |
| NFR-03 | 系统基线 | Android 8.0+（API 26）/ iOS 15.0+ |
| NFR-04 | 依赖成本 | 发送端只依赖 `cryptography`；移动端只用系统原生加密库 |
| NFR-05 | 首版分发 | 群内直发（APK / TestFlight），不走应用商店 |

## 6. 约束与假设

1. **安全边界是“躲扫描”，不是“抗逆向”**。根密钥内置在 App 里，被逆向就能解出；这个取舍是明确接受的，不要按“高安全”去设计验证和文案。
2. **QQ 客户端行为不可控**。改名、丢 MIME、清临时目录都可能发生，App 必须用魔数而不是后缀做判定。
3. **不做服务端**，所以没有吊销、没有远程配置、没有密钥下发。密钥轮换只能靠发版。
4. **群内直发**意味着没有商店灰度和强更能力，旧版本 App 会长期存在，密钥与协议必须考虑向后兼容。
